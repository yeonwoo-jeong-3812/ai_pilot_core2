# L4 FDM/물리 계층 비교 — core-live vs core2

> 대상: core-live `control/plant.py` (198 LOC) ↔ core2 `aircombat/fdm/plant.py` (191 LOC)
> 방법: 전체 파일 diff + 상태벡터·적분·엔진배선 대조.

## 결론 먼저: **동률(사실상 동일 코드)**

두 파일은 **`_find_jsbsim_root()` 단 한 함수를 제외하고 바이트 단위로 동일**하다. `F16Plant` 클래스, 상태벡터 매핑, 입력 매핑, `set_ic`/`start_engines`/`trim`/`step`/`get_state`/`capture_state`/`restore_state`, `__main__` first-light 블록까지 전부 같다. 동료가 우리 F16Plant를 **그대로 복사**하고 배포경로만 정리한 것이다.

L4의 물리 충실도는 **정의상 동일**하다 — 둘 다 동일한 JSBSim + 동일한 F-16 native FLCS XML을 로드하므로 공력 모델·6-DoF 적분·FLCS 안정성증강이 같은 바이너리에서 나온다. 여기서는 우열이 갈릴 여지가 없다.

## 유일한 차이: JSBSim 데이터 루트 탐색

| | core-live | core2 |
|---|---|---|
| `_find_jsbsim_root()` | **3-경로 폴백 탐색** (번들 → sdk vendored → core 자신), `aircraft/f16` 존재 확인 후 선택 | **단일 하드코딩** `../../jsbsim_data` |
| 성격 | 여러 배포 컨텍스트(모노레포/sdk/코어)에서 데이터를 찾는 robust 로직 | 저장소 루트 `jsbsim_data/` 하나만 가정한 정제형 |

```python
# core-live: 배포 컨텍스트 3종 폴백
def _find_jsbsim_root():
    here = os.path.dirname(__file__)
    for c in (
        os.path.join(here, "..", "jsbsim_data"),                    # 번들(우선)
        os.path.join(here, "..", "..", "ai-combat-core-main", ...), # sdk vendored
        os.path.join(here, "..", "..", "external_repo", ...),       # core 자신
    ):
        if os.path.isdir(os.path.join(c, "aircraft", "f16")):
            return os.path.abspath(c)
    return os.path.abspath(os.path.join(here, "..", "jsbsim_data"))

# core2: 단일 경로
def _find_jsbsim_root():
    here = os.path.dirname(__file__)
    return os.path.abspath(os.path.join(here, "..", "..", "jsbsim_data"))
```

**해석:** core-live의 다중경로는 연구 substrate가 여러 배포 형태(sdk vendored, external_repo, 번들)를 오가며 겪은 흔적이다. core2는 `jsbsim_data/`를 저장소 루트에 self-contained로 번들해 이 흔적을 지웠다. **배포 정합성은 core2가 약간 낫고**(경로 가정 1개, 예측가능), **배포 강건성은 core-live가 낫다**(위치 3종 자동탐색). 어느 쪽도 물리 결과에는 영향 없다.

## L4를 둘러싼 계층-인접 차이(플랜트 밖, 후속에서 다룸)

- **적분 구동 주파수**: 플랜트 `dt`는 호출자(스케줄러)가 정한다. core2 ARCHITECTURE는 연구 스택 물리 base를 **120Hz**로, L2=÷2(60Hz)·L1=÷6(20Hz) 다중레이트로 명시. core-live 연구 매치(`engine/match.py`)는 `control_hz=20 / log_hz=60`으로 구동. → **스케줄러(엔진) 계층 차이**이지 플랜트 자체 차이가 아니다. L1/엔진 비교에서 다룬다.
- **토너먼트 엔진 분리**: 두 plant 모두 "매치 엔진(.pyd)과 무관한 별도 연구 스택"임을 docstring에 명시. 대회 채점 엔진은 이 standalone plant가 아니라 별도 `.pyd`(JSBSim 60Hz 고정). → 연구 plant 비교는 채점과 직교.

## 판정

| 축 | 우위 | 근거 |
|---|---|---|
| 물리 충실도(공력·6-DoF·FLCS) | **동률** | 동일 JSBSim + 동일 F-16 native FLCS XML |
| 상태·입력 인터페이스 | **동률** | 10-state 부분집합·4-input 매핑 동일 |
| rollout capture/restore | **동률** | IC 경유 12-DOF 복원 로직 동일 |
| 배포 정합성 | core2 (미미) | 경로 가정 1개, self-contained 번들 |
| 배포 강건성 | core-live (미미) | 3-컨텍스트 자동탐색 |

**L4 총평:** core2는 우리 L4를 **그대로 채택**했다. 이 계층은 동료 v2가 "우리 new-engine 기반"임을 가장 명확히 보여주는 증거다 — 검증된 물리 기반을 손대지 않고 경로 위생만 정리했다. **우열 무의미(공유 기반)**. 진짜 우열은 이 위층(L3 제어·L2 가이던스·L1 전술)에서 갈린다.
