# L1 전술/BT 계층 비교 — core-live vs core2

> 대상:
> - core2 `tactics/{dsl.py(221), node.py(179), conditions.py(143), context.py(69), policy.py(45)}` — 화이트리스트 저작 DSL
> - core-live `bt/yaml_bt.py + policy_yaml/full_unified/full_unified_42.yaml + nodes/` + `bt/`(110 files 연구랩)
> 방법: DSL 안전성·어휘·chatter제어·표현력·검증결과 대조.

## 결론 먼저: **서로 다른 주인을 섬긴다 — 저작 프레임워크 vs 승리 에이전트**

L1은 두 프로젝트가 모두 크게 투자했으나 **목적이 다르다**:
- **core2 L1** = *안전한 참가자 저작 프레임워크*. 화이트리스트 검증 DSL + 교범인용 조건 어휘 + Commit/Cooldown chatter 데코레이터. 대회 플랫폼에서 참가자가 신뢰없이 제출하는 트리를 안전·감사가능하게 실행.
- **core-live L1** = *실제 승리 에이전트 + 연구랩 + 광역 호환*. 42/42 FullUnifiedPolicy(yaml+py 틱-동일) + cost-argmax 선택 + 커스텀 stateful 노드 + 970 legacy 트리 호환(bt-editor 어휘 100%).

즉 이 계층은 정면 우열이 아니라 **역할 분담**이다.

## 축 1: DSL 안전성 — 화이트리스트 vs 임의 파이썬

| | core2 | core-live (yaml_bt) |
|---|---|---|
| 액션/조건 | **화이트리스트**(`_ACTION_KEYS`, `CONDITIONS` 레지스트리) | 35조건+37액션 매핑 + **커스텀 파이썬 노드** |
| 파라미터 검증 | `inspect.signature` 대조, 미지키 ValueError | params dict → 커스텀 클래스 생성자 |
| include/외부코드 | 상대경로만·`..`거부·깊이5 샌드박스 | `custom_{conditions,actions}.py` 임의 실행 |
| 신뢰 모델 | **미신뢰 제출 안전**(임의 파이썬 없음) | 신뢰 필요(임의 노드 로드) |

**core2 우위(안전):** 참가자 제출을 신뢰 없이 실행하려면 화이트리스트가 필수다. 미지 키·범위밖 값을 조용히 삼키지 않고 즉시 ValueError — 오타·악의 코드 차단. core-live yaml_bt는 커스텀 파이썬 노드를 로드하므로 표현력은 크지만 미신뢰 제출엔 부적합(챔프 저작·연구용).

## 축 2: 조건 어휘 — 교범인용 vs obs-직결

| | core2 | core-live |
|---|---|---|
| 조건 수 | 18종 | 35종 |
| 근거 | **전부 BEM Ch.4 인용**(foe_threat 4.4.9, overshoot_risk 4.4.7.2, initial 등) | 대부분 obs 직접(거리·각도·에너지) |
| BFM 국면 어휘 | **HABFM/OBFM/DBFM** 명시 wrapper(is_head_on/offensive/defensive) | 없음(obs 술어 조합) |

**core2 우위(설명가능성):** 18조건이 전부 교범 조항에 앵커되고, HABFM/OBFM/DBFM 국면을 이름있는 술어로 노출한다("저작·설명을 BFM 용어로"). L2 doctrine과 동일한 감사철학. core-live 어휘는 넓지만(35, 970 legacy 커버) obs 직결이라 교범 근거가 약하다.

## 축 3: chatter 제어 — 재사용 데코레이터 vs 임시 stateful 노드

| | core2 | core-live |
|---|---|---|
| 방식 | **Commit/Cooldown DSL 데코레이터** + dwell 히스테리시스(0.3s) | 커스텀 stateful 노드(empty-dive latch, dive-onset latch) |
| 재사용성 | 어느 트리든 `{commit:{duration_s,cooldown_s,child}}` | 챔프별 하드코딩 latch |
| 감사 | trace에 latch/hold/replay/cooldown 기록 | per-tick 계측(사후) |

**core2 우위(구조):** Commit(기동 duration 잠금+snapshot/replay+cooldown)과 Cooldown(재진입 차단)을 **재사용 DSL 데코레이터**로 팩터링했다. core-live는 동일한 chatter 문제(`engine/analyze_chatter.py`가 존재하는 이유)를 챔프마다 임시 stateful 노드(empty-dive latch 등)로 푼다 — 작동하지만 재사용·감사가 약하다. **이것은 core2가 우리 pain point를 깔끔히 해결한 사례**로, 역이식 가치 큼.

## 축 4: 선택 패러다임 — 우선순위 selector vs cost-argmax

| | core2 | core-live |
|---|---|---|
| 선택 | **우선순위 Selector**(첫 매칭 브랜치 승) | **cost-weighted argmax**(전술별 비용 최소) |
| 성격 | 하드 우선순위(딱딱, 감사 쉬움) | 소프트 경쟁(강건, 경계 부드러움) |
| 근거 | 6분기 DEFAULT_SPEC | 일반해 루프1~16 cost 트리 |

**core-live 우위(강건성):** 챔프는 전술을 하드 우선순위가 아니라 **cost argmax**로 고른다 — 경계에서 딱 끊기지 않고 부드럽게 경쟁해 chatter·knife-edge를 줄인다. 이는 우리 일반해 연구의 핵심 산물([[final-bt-cost-unified-17of17]]). core2의 우선순위 Selector는 감사가 쉽지만 경계에서 딱딱하다(dwell로 완화). **단 두 방식은 상보적** — cost argmax도 감사가능하게 만들면(비용 항 trace) 양쪽 장점 결합 가능.

## 축 5: 검증된 결과 + 광역 호환

| | core2 | core-live |
|---|---|---|
| 레퍼런스 에이전트 | DEFAULT_SPEC(합리적 6분기, **승률 미측정**) | **42/42 FullUnifiedPolicy**(canonical17+heldout25 무패) |
| legacy 호환 | 없음(새 DSL 전용) | **970 legacy 트리** 자동실행(bt-editor 100%) |
| 이중 표현 | YAML만 | **.yaml ↔ .py 틱-동일**(설명가능+실행형) |

**core-live 우위(실증·호환):** core-live L1만이 **실제 42/42 챔프**를 갖고, .yaml↔.py 틱-동일로 설명가능성과 실행성을 동시 만족(대회 제출형). 970 legacy 트리를 손포팅 없이 실행해 MC rollout 대항군 커버리지를 확보. core2 DEFAULT_SPEC은 구조적으로 합리적이나 전투 실증이 없다.

## 판정표

| 축 | 우위 | 근거 |
|---|---|---|
| DSL 안전성(미신뢰 제출) | **core2** | 화이트리스트·inspect검증·샌드박스 include |
| 조건 어휘 교범근거·국면어휘 | **core2** | 18조건 BEM인용 + HABFM/OBFM/DBFM |
| chatter 제어 구조·재사용 | **core2** | Commit/Cooldown 데코레이터 |
| 선택 패러다임 강건성 | **core-live** | cost-argmax(소프트 경쟁) |
| 표현력·커스텀 노드 | **core-live** | stateful 커스텀 노드(챔프 표현) |
| legacy 호환·대항군 커버 | **core-live** | 970 트리, bt-editor 100% |
| **검증된 챔프 + 이중표현** | **core-live** | 42/42, .yaml↔.py 틱-동일 |

## L1 총평

**두 L1은 경쟁이 아니라 역할 분담이다.** core2 L1은 *플랫폼이 참가자에게 주는 안전한 저작 프레임워크*로 우수하다 — 화이트리스트 안전성, 교범인용 어휘, Commit/Cooldown 재사용 데코레이터. core-live L1은 *그 프레임워크로 만들 수 있는 최고의 에이전트*(42/42)와 *그것을 생산한 연구랩*, 그리고 *970 legacy 광역 호환*으로 우수하다.

**핵심 통찰:** core2의 안전·감사 DSL로는 core-live의 42/42 챔프(cost-argmax + empty-dive gate)를 **표현할 수 없다**(화이트리스트에 cost·custom-latch 어휘 없음). 역으로 core-live의 표현력 있는 yaml_bt는 미신뢰 제출엔 위험하다. → **이상적 L1 = core2의 안전·감사 골격 + core-live의 cost-argmax·chatter-latch를 화이트리스트 노드로 편입.**

**흡수 후보:**
- FROM core2 → core-live: ①**Commit/Cooldown 데코레이터**(우리 임시 latch를 재사용 노드로, chatter pain 해소, 최우선), ②**교범인용 조건 어휘**(HABFM/OBFM/DBFM, 감사가능성), ③**화이트리스트 검증**(대회 제출 안전).
- FROM core-live → core2: ①**cost-argmax 선택 노드**(하드 우선순위의 knife-edge 완화), ②**42/42 챔프**를 core2 DSL로 재표현 시도(표현 한계 확인용), ③**970 legacy 호환 인터프리터**(대항군 커버리지).

**검증 실험(후속):** core2 DEFAULT_SPEC(+doctrine) 에이전트를 우리 하네스(canonical17+heldout25)에 붙여 승/무/패 실측 — core2의 교리기반 우선순위 트리가 몇 승 내는지 최초 측정. 그리고 우리 42/42 챔프를 core2 화이트리스트 DSL로 표현 시도 → "안전 DSL의 표현 한계"를 정량화.
